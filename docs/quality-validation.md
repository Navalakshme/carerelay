## Reproduce

Use Node.js 22. Run `npm ci --ignore-scripts`, `npm run check`, `npm test`, `npm run build` and `npm audit --audit-level=moderate`.

Database and browser integration tests require a fresh disposable PostgreSQL database named `carerelay_test` on loopback, a `psql` executable, and `DATABASE_URL`. The test runner refuses other database hosts/names. Run `npm run test:db`, `npx playwright install --with-deps chromium`, then `npm run test:browser`. The GitHub workflow provisions PostgreSQL 17. Tests use synthetic identities without usable login credentials. The browser suite replaces only the identity provider; it executes the production HTTP handler and real database functions. Hosted Supabase authentication/email is a separate integration boundary.

`002_security_tests.sql` tests the original schema before 003. `004_upgrade_tests.sql` tests the upgraded schema and rolls back its fixtures. `tests/concurrency.mjs` uses two actual concurrent database clients to prove one ownership winner. No production records are required for automated tests.

## Product boundaries

- Reminders are durable **in-app inbox records**, generated by a database job every minute. They are visible when the recipient opens CareRelay. Email, SMS, push notifications and emergency monitoring are not connected.
- Plans support 1â€“30 daily occurrences at the circle's local wall time. This is a bounded schedule, not an indefinite recurrence engine. Prescription details come from the existing clinician prescription.
- State includes at most 300 occurrences from the past 7 and next 31 days, 100 latest questions, 100 latest plans and 50 latest source events. History is paginated. Briefs explicitly declare their scope; they do not claim to include the complete lifetime ledger.
- Idempotency keys are retained for seven days. An invitation retry cannot reveal its code again; the elder reviews/revokes unused invitations before creating a replacement. Only a code hash is retained, including in request payload fingerprints.
- Removal retains completed ownership metadata, releases open assignments and revokes unused invitations. Access is checked again before cached responses are replayed.
- Automated axe checks do not certify full WCAG conformance. Manual screen-reader testing, broader device testing, load testing, independent penetration testing and backup restoration exercises remain additional assurance work.
- Supabase email confirmation remains enabled. Hosted email delivery and recovery depend on the project's Auth configuration and SMTP service. No custom SMTP delivery claim is made.
- Account deletion and retention policy need a considered production workflow. No health-record purge is added as a hackathon shortcut.
- Authentic Google Antigravity work must be completed and documented if required by the organizer. Codex implementation must not be presented as Antigravity-generated evidence.

## Operations

For an existing project, apply 003 and 006 once, then 005 to schedule `care_private.tick_all()` each minute. Verify the job in `cron.job` and recent successful executions in `cron.job_run_details`. Only the database owner can invoke the worker; clients cannot choose the server clock. Post-migration validation is 004. Do not re-run 001 or 003 on an already migrated project.

Monitor Vercel 5xx counts and database cron failures. Application error logs contain only an event name and status, never request bodies, account emails, tokens or care details. The function's provider fetch has a 12-second timeout; the browser request has a 20-second timeout and does not silently queue offline mutations.

Before a production restore, create an encrypted database backup using the account owner's approved Supabase process, restore it into a separate project, apply subsequent migrations and re-run permission tests with disposable identities. Do not commit exports or use the public repository as a backup. No restore exercise is claimed here.
